# Initial audit — third-year business-computing student

Method: source review of the existing `app.js`, not browser gameplay. This is the preliminary audit and does not count toward the requested five-round review.

## Student profile used

A third-year business-computing student who has built a small HTML/JavaScript project, written simple SQL queries, made an Excel report, and worked in a group project. They have not deployed production services or mastered UX research. They can read a short code example but need explanations of unfamiliar syntax. They want a business analyst, junior web, database support, or QA placement according to evidence in their CV.

## Blocking learning and usability concerns

1. **Job matching is not believable.** A score starts at 42 and can count the same CV words more than once. A student with Excel and basic HTML can appear suitable for unrelated specialist jobs. Show which requirements the CV actually supports, which are missing, and why jobs outside that skill family score low. Merely wanting a role must not count as having its skills.
2. **Training does not teach job tasks.** The same modules repeat with general communication answers. A business-computing student needs SQL query/output exercises, data-cleaning examples, JavaScript bug fixes, test cases, and UI comparison tasks. After a mistake, show a small worked example, not just an instruction to be more careful.
3. **The contextual answer is visually identifiable.** The longest answer combines the original correct response and the new condition. I could choose it without understanding the condition. Use plausible, similar-length options and test actual results.
4. **The perfect interview gate discourages experimentation.** Any non-max answer causes an entire retake. A reasonable partial answer should be reflected in the appropriate interview dimension, with a clear route to training in that dimension. A student should learn why they failed without memorizing a full answer sequence.
5. **The game gives little sense of an office.** I would like to choose a desk, talk to a peer, ask a mentor, or approach a lead. Those people should remember if I helped, ignored, blamed, or updated them. A conversation should sometimes create a later task, not always merely return to the next survey item.
6. **Feedback is difficult to perceive.** The month screen shows current numbers after an answer, but not the signed change. Show `คุณภาพ +2`, `พลังงาน −3`, a named character's emotion, and one concise reason. Show a picture in the resulting scene too.
7. **Unrelated animal jokes distract from the task.** A serious data or health problem should not contain a randomly attached cat joke. Animals may appear in an authored scene when there is a real cause, but must not be inserted into unrelated prompts.
8. **Consequences need a visible chain.** If I hide an error, I should later see the same error reach a colleague, lose trust, and get a concrete chance to disclose/repair it. The game should explain that callback briefly. A worse ending should reflect my decisions rather than simply an opaque threshold.

## Acceptance checks for the redesigned build

- Compare the same modest CV against developer, database, UX, QA, and marketing roles; scores must differ for evidence-based reasons and no unrelated specialist role should get a high score.
- Try an empty CV, a CV listing desired skills only, and a CV denying experience. They must not gain the same evidence as a project describing actual work.
- Play at least five distinct training topics across JavaScript, SQL, UX, testing, and communication. Inspect an incorrect answer and check that its worked explanation teaches a usable fact.
- Check that every decision and result screen has a meaningful scene, that player avatar choices persist, and that signed stat changes and NPC reaction are visible immediately.
- Initiate optional office conversations. Check that prior interactions affect dialogue, and that the office still permits returning to the current task without a dead end.
- Follow a harmful choice into a later consequence and then try a repair path. Check the same people/problem appear in the callback.
- Follow one careful and one careless run toward different endings. Avoid using knowledge of hidden score constants to decide player choices.
- Confirm that graph links, node scenes, and ending leaves are present in actual data and inspectable; a big advertised number alone does not meet this requirement.

## What would make it enjoyable

A short workday loop: look around the office → choose a person or task → solve a concrete problem → see an immediate visual reaction → discover a consequence later. Mix a code task with a social choice or a quiet exploration scene. Give a student understandable setbacks and a way to repair some of them, rather than requiring endless perfect quizzes.
